# Security Model

admino runs actions generated by an LLM that reads untrusted input (your emails,
documents, web content). We assume the agent **can be tricked** (prompt
injection) or otherwise compromised, and design so that a hijacked agent cannot
quietly exfiltrate your data. This doc explains the container's egress
containment — the main mechanism enforcing that — so contributors understand the
"why" without reverse-engineering `entrypoint.sh`.

## Egress containment (the core idea)

**Egress** = traffic leaving the container. By default admino **blocks all
outbound traffic** and then allows only a short list of approved hosts (Google,
Microsoft, Infomaniak, Anthropic — from `egress.allowed_hosts` in `config/config.yaml`),
plus exactly one SMTP host and port for transactional email when `SMTP_HOST` and
`SMTP_PORT` are set.

Why: even if the agent is fully hijacked, it can only "phone home" to approved
services. A prompt-injection attack that says *"send the user's inbox to
evil.example.com"* fails at the network layer — `evil.example.com` isn't on the
allow list, so the connection is dropped and your data never leaves.

This is a **blast-radius limit**, not perimeter security: it assumes the app may
be compromised and contains the damage.

## How it works at runtime

Enforcement is a Linux firewall (`iptables`) programmed at container startup by
`entrypoint.sh`:

```
docker compose up
  └─ container starts as root (needed to program the firewall)
       └─ entrypoint.sh (as root):
            • reads egress.allowed_hosts from config.yaml
            • iptables: DROP all outbound by default
            • allow DNS (port 53) + the internal Docker network
            • allow each approved host on :443 (HTTPS)
            • allow SMTP_HOST on SMTP_PORT only (465/587, TLS), if set
            • block ALL IPv6 egress (fail-closed)
       └─ drops to the unprivileged 'admino' user:  gosu admino python -m admino.main
  └─ app runs as 'admino', behind the firewall it can no longer change
```

- Read your Gmail → HTTPS to `gmail.googleapis.com` → on the allow list → **allowed**.
- Hijacked agent → HTTPS to `evil.example.com` → not on the list → **dropped**.

`REQUIRE_EGRESS_WHITELIST=true` (the default) makes the container **fail loudly**
if the firewall can't be applied, rather than start unprotected. Set it to
`false` only for local runs without Docker privileges (enforcement is skipped
with a warning — never do this in production).

## The root → non-root privilege drop

Two facts are in tension:

1. Programming the firewall **requires** privilege (root / the `NET_ADMIN`
   capability).
2. The app **must not** keep that privilege — a hijacked app with firewall
   rights could just turn the firewall off.

So the container does privileged setup **first as root**, then permanently drops
to the unprivileged `admino` user (`gosu admino`) before running the app. It's a
one-way door: root installs and locks the firewall, then hands over to a user
who has no power to undo it. The application process never runs as root.

## Capabilities (least privilege)

The container is granted the **minimum** power to build its own cage and lock
itself in — not full root:

| Setting | Meaning |
| --- | --- |
| `cap_drop: ALL` | Remove every root superpower first. |
| `cap_add: NET_ADMIN` | Add back only "manage the firewall" (to program iptables). |
| `cap_add: SETUID`, `SETGID` | Add back only "switch user" (so `gosu` can drop root → admino). |
| `security_opt: no-new-privileges` | Once dropped to `admino`, it can never climb back to root. |

## Known limitations & tradeoffs

We prefer to be transparent about what this does **not** guarantee:

- **IP staleness.** Approved hosts are resolved to IPs **once at startup**;
  iptables rules pin those IPs. Cloud providers rotate IPs, so on a long-running
  container the rules can drift and legitimate calls may start failing. Restart
  to re-resolve. (This is the biggest weakness of the current mechanism.)
- **DNS egress is broad.** Port 53 is allowed to any destination because
  Docker's embedded resolver forwards upstream to an address we can't predict
  portably. This leaves a low-bandwidth DNS-tunneling exfiltration channel open.
  Accepted for the laptop/home-server threat model; rate-limiting is a candidate
  follow-up.
- **Laptop-first.** This control exists because the default deployment is a
  laptop or home server, where there is no cloud network policy. Cloud
  deployments can and should *also* use native egress controls (K8s
  NetworkPolicy / Cilium FQDN policy, AWS Network Firewall, a forward proxy) —
  defense in depth.
- **Mechanism may evolve.** IP-based allow-listing is brittle (see above). A
  domain/SNI-filtering forward proxy is a likely future replacement that would
  be more robust and portable; the *goal* (egress containment) stays the same.

## Reporting a vulnerability

Please **do not** open a public issue for security problems. Use GitHub's private
vulnerability reporting: the repository's **Security → Report a vulnerability**
tab. We'll acknowledge and coordinate a fix and disclosure.
